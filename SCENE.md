# Scene Data Loading and Updates

This document explains how geometry data is loaded and updated in both native and web environments for the pointcloud rendering system.

## File Structure

The system uses two main data files:

- **`session.json`** - Contains the complete geometry data (vertices, indices, pointcloud instances, transforms)
- **`session_metadata.json`** - Contains only a timestamp for efficient change detection

Both files are located in `/wink/data/` and served from `/geometry/` path on the web.

## Native Environment

### Initial Loading
- Geometry is loaded synchronously from local files at startup
- Falls back to embedded geometry data if files are not found
- Uses absolute file paths resolved from `CARGO_MANIFEST_DIR`

### File Watching
- Background thread monitors `session.json` and `session_metadata.json` for changes
- Uses OS file system notifications for immediate change detection
- Updates are sent through a channel to the main render thread
- No throttling - changes are applied immediately when detected

### Update Flow
```
File Change → OS Notification → Background Thread → Channel → Render Thread → GPU Update
```

## Web Environment (WASM)

### Initial Loading
- Geometry is fetched asynchronously from `/geometry/session.json`
- Falls back to embedded geometry data if fetch fails
- Uses browser's fetch API with error handling

### Smart Polling System
- **Metadata Polling**: Checks `/geometry/session_metadata.json` every 1000ms
- **Full Geometry Loading**: Only when metadata timestamp changes
- **Throttled Updates**: Prevents excessive network requests and parsing

### Performance Optimization
The web environment uses a two-stage approach to minimize bandwidth and improve performance:

1. **Lightweight Metadata Check** (1KB file)
   - Contains only a Unix timestamp
   - Polled frequently (every 1 second)
   - Minimal network overhead

2. **Full Geometry Loading** (potentially 100MB+ file)
   - Only fetched when metadata timestamp changes
   - Parsed and applied to GPU buffers
   - Cached locally until next change

### Update Flow
```
Timer → Metadata Fetch → Timestamp Compare → Full Geometry Fetch → Parse → GPU Update
```

## Data Generation

Geometry data is generated by the `openmodel` crate:

- **`openmodel/src/main.rs`** generates pointcloud data and writes both files
- **`session.json`** contains complete serialized geometry
- **`session_metadata.json`** contains only the current Unix timestamp
- Files are written atomically to prevent partial reads during updates

## Development Workflow

### File Watching During Development
The development server (`npm run dev`) includes a file watcher script:

- **`docs/.vuepress/scripts/watch-geometry.js`** monitors data files
- Automatically copies updated files to the web server's public directory
- Enables real-time geometry updates during development

### Building and Deployment
- Native builds include embedded fallback geometry data
- Web builds rely on served geometry files
- Large geometry files should be served with appropriate caching headers

## Performance Characteristics

### Native
- **Pros**: Immediate file change detection, no network overhead
- **Cons**: File I/O on main thread during initial load
- **Typical Update Latency**: <10ms

### Web
- **Pros**: Non-blocking async loading, efficient change detection
- **Cons**: Network latency, periodic polling overhead
- **Typical Update Latency**: 1-2 seconds (depending on file size and network)

## Configuration

Key constants that control the behavior:

```rust
// Web polling interval for metadata checks
const GEOMETRY_POLL_INTERVAL_MS: u64 = 1000;

// File paths
const SESSION_FILE: &str = "session.json";
const SESSION_METADATA_FILE: &str = "session_metadata.json";
```

## Troubleshooting

### Common Issues

1. **Files not updating on web**: Check that the development file watcher is running
2. **High CPU usage on web**: Verify polling interval is not too aggressive
3. **Memory issues with large files**: Ensure old geometry data is properly dropped
4. **Channel disconnection on native**: Check that the background thread is not panicking

### Debugging

Enable console logging to trace the update process:
- Native: Standard Rust logging
- Web: Browser console shows fetch attempts and timestamp comparisons
